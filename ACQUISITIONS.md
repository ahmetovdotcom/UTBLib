# Поступления и экземпляры

## Два независимых способа учёта

**Новое поступление** создаётся в боковом меню «Поступления» → «Новое поступление». Укажите дату, источник, накладную (необязательно), выберите одну или несколько книг из каталога. Для каждой строки задаются количество, цена одного экземпляра, валюта, сигла и примечание. Регистрация атомарно создаёт партию и её экземпляры. Новые названия сначала сохраните в каталоге. Исправление зарегистрированных сведений выполняется с причиной и историей; см. STOCK_OPERATIONS.md.

**Имеющийся фонд** добавляется в редактировании сохранённой записи → «Экземпляры» → «Создать экземпляр». Это один экземпляр без накладной и без поступления. Он виден в общем списке экземпляров книги, но не попадает в журнал и статистику новых поступлений для будущего КСУ. Можно указать инвентарный номер, штрихкод, сиглу, цену, валюту, известную дату и источник, дату проверки и примечание. Пустые номер и штрихкод генерируются автоматически. Пустая цена отличается от нулевой.

Сохранение библиографического описания, в том числе с заполненными 541$n, 541$h, 990$c и 990$w, само по себе ничего не создаёт. Эти исторические MARCSQL-поля не служат счётчиком фонда. Блок «Первое поступление» убран из новой карточки. Для совместимости с уже отправленными запросами прежнего интерфейса API ещё принимает явно заданный `initial_acquisition`; новый интерфейс его не отправляет.

Инвентарные номера и штрихкоды уникальны среди всех экземпляров. Автоматические идентификаторы имеют вид `INV-<UUID>` и `BC-<UUID>`; печать этикеток пока не реализована. В существующем экземпляре редактируются номер, штрихкод, сигла, проверка и примечание с сохранением истории и версии. Цена, дата и источник зафиксированы при регистрации; для экземпляров партии исправление выполняется через поступление; индивидуальная финансовая корректировка имеющегося фонда пока не реализована.

## Защита от повторов

- Каждая отправка новой записи, поступления и отдельного экземпляра получает UUID операции.
- UUID и хеш нормализованного запроса сохраняются в базе в той же транзакции.
- При повторе того же запроса возвращается уже существующий результат.
- При повторе ключа с другим содержимым возвращается 409.
- PostgreSQL advisory transaction lock сериализует одновременные повторы; уникальные ограничения — дополнительная защита.
- Номер накладной не является уникальным ключом: одинаковые номера возможны у разных поставщиков/лет, одна накладная может содержать несколько названий.
- Интерфейс сохраняет отправленный запрос в sessionStorage до подтверждения и предлагает восстановить результат после сетевой ошибки/перезагрузки. Восстановление работает в той же вкладке/сессии браузера. Потеря всей сессии требует сначала проверить каталог/поступления; повторный ручной ввод как новой партии получает новый UUID.
- Общее ограничение одной партии — 100 строк и 10000 экземпляров.

## Основа для будущего КСУ

`acquisitions` — неизменяемый заголовок зарегистрированного поступления (накладная, дата, источник, примечание, время регистрации).
`acquisition_lines` — документ, его заглавие на момент поступления, количество, точная десятичная цена, валюта, исходная сигла и примечание.
`copies` — идентификаторы и индивидуальные сведения. Для новой партии сохраняется `line_id`. Для имеющегося фонда `line_id` пуст, а `record_id` указывает книгу напрямую; цена, дата и источник хранятся в экземпляре. Проверка базы допускает ровно один из этих способов связи.
`copy_history` — история редактирования индивидуальных сведений. Доступ проверяется по учётной записи и правам. Персональное авторство в старом журнале экземпляров пока не записывается.
`record_creations` — квитанции идемпотентности первого сохранения.

Удаление библиографической записи с поступлениями или экземплярами имеющегося фонда запрещено, в том числе внешними ключами PostgreSQL. Удаления экземпляров и зарегистрированных поступлений через API нет. Исправления поступлений, отмена ошибочной регистрации и списание реализованы отдельными операциями с историей (STOCK_OPERATIONS.md). Перемещения для КСУ пока не реализованы. Полноценный КСУ, его печатная форма, баланс фонда в эту версию **не входят**.

`GET /api/acquisitions/summary?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD` выдаёт число поступлений, различных библиографических записей, экземпляров и суммы по каждой валюте отдельно. Даты включаются в диапазон по дате поступления. `unpriced_count` показывает экземпляры без известной цены; известные суммы не выдаются за полный итог при наличии таких экземпляров. Это техническая сводка поступлений, не утверждённая форма КСУ.

## API

Все маршруты требуют сеанс пользователя и соответствующие права; изменения также требуют `X-CSRF-Token`. См. AUTH.md.
- `POST /api/records`: необязательный `request_key`, `initial_acquisition` с датой, валютой, примечанием. Оба нужны только для совместимости с явно запрошенным первым поступлением старого клиента; само наличие 541$n ничего не создаёт. Количество/цена/источник/накладная/сигла извлекаются сервером из MARC.
- `PUT /api/records/{id}`: редактирование описания, без создания поступлений.
- `POST /api/acquisitions`: `request_key`, `invoice`, `received_on`, `source`, `note`, `lines` с `record_id`, `quantity`, `unit_price`, `currency`, `sigla`, `note`.
- `GET /api/acquisitions?record_id=...&offset=0&limit=20`: партии, включая все строки общей накладной.
- `GET /api/records/{id}/copies?q=...&offset=0&limit=50`: количество и экземпляры; поиск по инвентарному номеру или штрихкоду.
- `POST /api/records/{id}/copies`: создание одного экземпляра имеющегося фонда; UUID `request_key`, необязательные идентификаторы, цена/валюта, дата/источник, сигла, проверка, примечание. Накладная не принимается. Повтор того же запроса не создаёт второй экземпляр.
- `PUT /api/copies/{id}`: `version`, `inventory_number`, `barcode`, `sigla`, `checked_on`, `note`.
- `GET /api/copies/{id}/history`: прежние/новые индивидуальные сведения.

## Миграция и проверка

Миграция `0004_acquisitions` создаёт только новые таблицы, без изменения существующих MARC-записей и без автоматического создания экземпляров из импортированных количеств. Импорт экземпляров из MARCSQL требуется отдельный: нельзя восстановить их индивидуальные инвентарные номера по одному количеству.

Обычный запуск: `docker compose up -d --build`. Alembic применяется при старте API. Перед развёртыванием сделана локальная резервная копия рабочей базы, а миграция проверена на её изолированной копии с 9867 записями: контрольная сумма записей до/после совпала. Для отката приложения можно вернуть прежний образ, оставив новые таблицы; не выполняйте downgrade после начала рабочего учёта — он удаляет новые таблицы и их данные. Исправления схемы после запуска оформляются следующими миграциями.

Тесты: `docker compose run --rm --no-deps -e ADMIN_KEY=test-secret -e DATABASE_URL=sqlite:// api python -m pytest -q`. Дополнительный интеграционный тест `tests/test_postgres_acquisitions.py` включается только переменной `ACQUISITIONS_TEST_URL=http://localhost:8097` и предназначен для отдельной одноразовой копии PostgreSQL, где разрешено создание тестовых записей.

Миграция `0005_existing_copies` допускает экземпляры без строки поступления и добавляет их индивидуальные сведения. Существующие связи с партиями не меняются. Downgrade запрещён при наличии экземпляров имеющегося фонда: используйте следующую исправляющую миграцию. Имеющийся фонд будет отдельной составляющей начального остатка будущего КСУ; сейчас сводка `/acquisitions/summary` отражает только новые поступления.
