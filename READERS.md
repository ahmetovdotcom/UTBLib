# Читатели и посещения

Разделы работают из локальной PostgreSQL, включая отсутствие/недоступность AD и Platonus. Импорт не создаёт учётные записи сотрудников, пароли и права. `reader_profiles.user_id` — необязательная уникальная связь с существующим сотрудником; автоматически по ФИО/email она не устанавливается. Входы на сайт считаются только для явно связанной учётной записи по журналу входов с момента внедрения этого модуля. История до внедрения не восстановлена.

## Локальный запуск

```sh
docker compose up -d --build --wait
```

Добавочная миграция `0015_readers_visits` выполняется при старте API. Она создаёт реестр, идентичности источников, пункты обслуживания, постоянные счётчики билетов, фото, журнал посещений, аудит, журнал синхронизации и конфликтов. Существующие таблицы и записи не очищаются. Перед обновлением рабочей установки выполните её обычный backup. Не используйте `down -v`.

Страницы: http://localhost:8096/#readers и http://localhost:8096/#visits. Администратор назначает права в «Пользователи и права». Для работы с реестром нужны `readers.registry.view`, для редактирования — дополнительно `readers.registry.edit`, для ИИН/даты рождения — `readers.personal_data.view`; отдельно экспорт, аналитика, печать билета, журнал синхронизации. Рабочее место сканирования использует `visits.record`, журнал и показатели — `visits.view`. Обычные категории student/teacher/staff административных прав не дают.

Сначала добавьте свой реальный пункт обслуживания внизу реестра. Создайте карточку или выполните согласованный импорт. Номер билета и штрихкод присваиваются один раз атомарным счётчиком, не меняются при смене курса и повторной печати. Настройка `READER_TICKET_PREFIX`, JSON `READER_FACULTY_CODES` действует только на новые билеты. `RDR` + 8 цифр — отдельный Code 128. Печать при масштабе 100%, с сохранением белых полей вокруг кода. Никакого ИИН или пароля в коде нет.

Посещения: USB HID-сканер вводит код и Enter. В пределах 10 минут повтор возвращает ту же запись даже на другом пункте. В PostgreSQL строка читателя блокируется на проверку/вставку. Повтор не продлевает время. Блокировка читателя не снимается. Время хранится в UTC; границы календарных суток и показатели — Asia/Almaty. Нет учёта выхода, длительности и присутствующих «сейчас».

Книговыдача/штрафы в UTBLib пока отсутствуют: показано «данные модуля недоступны», обходной лист отключён. Это не означает проверенное отсутствие долгов. Wallet и физический турникет не реализуются.

## Конфигурация внешних источников

Ничего не подключено автоматически. Скопируйте `.env.readers.example` в `.env.readers`, заполните владельцем подтверждённые значения; файл исключён из Git. Не копируйте секреты старого приложения. Дополнительный `compose.readers.yaml` подключает окружение к API и отдельному исполнителю. Основная БД остаётся PostgreSQL; Platonus — отдельный read-only MySQL. `PLATONUS_ENABLED=false` и `AD_ENABLED=false` по умолчанию.

Недостающие внешние сведения: схема/учебный год Platonus; подтверждённые колонки и значения статусов; параметры AD, фильтр технических аккаунтов и нестандартные атрибуты; подтверждённая AD→Platonus связь; реквизиты MySQL, SSH, CA и закреплённый SSH host key. Для начала работы интерфейса они не требуются.

`PLATONUS_ACADEMIC_YEAR` рекомендуется задать явно. Пустое значение: год начала учебного года, переход 1 сентября (январь–август = предыдущий год). Перед чтением adapter проверяет наличие таблиц/полей через information_schema; имена/типы можно дополнительно проверить владельцу:

```sql
SELECT TABLE_NAME,COLUMN_NAME,DATA_TYPE
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA=DATABASE()
ORDER BY TABLE_NAME,ORDINAL_POSITION;
```

Студенты: `isStudent=1`, наличие текущего учебного года через studentstudygroup/studygroups, DISTINCT, постранично StudentID. Преподаватели: tutors.deleted=0, отдельный TutorID. Факультет берётся через подтверждённые joins из исходного проекта. Статусы и enum НЕ угадываются. `PLATONUS_INACTIVE_*_STATUSES`, `PLATONUS_GENDER_MAP`, `PLATONUS_DEGREE_MAP` — JSON; флаг `PLATONUS_STATUS_MAPPING_CONFIRMED` включается владельцем только после проверки правил. Учётная запись MySQL: исключительно необходимые SELECT; сессия дополнительно read-only, таймауты/пакет 500. Даже SELECT создаёт нагрузку.

AD: только LDAPS с проверкой сертификата или STARTTLS; проверку отключить нельзя. Обязательна LDAP pagination, отключённые аккаунты исключены. Владелец должен настроить фильтр технических аккаунтов и установить `AD_FILTER_CONFIRMED=true`. `AD_ATTRIBUTE_MAP` — JSON сопоставления локального поля и реального LDAP атрибута. По умолчанию используется профиль КазУТБ из исходного проекта, включая platonusUserId/platonusUserType/platonusUserStatus. `AD_ATTRIBUTE_MAP` и `AD_PLATONUS_TYPE_MAP` позволяют переопределить его для другой схемы. Связь разрешается флагом `AD_PLATONUS_LINK_CONFIRMED=true`. Само совпадение имени, email/телефона не связывает людей.

## SSH-туннель

Владелец предоставляет отдельный ключ и проверенный fingerprint сервера. `known_hosts` должен быть подготовлен после проверки fingerprint независимым каналом, а не слепого принятия ключа. Ключ/known_hosts монтируются read-only. В Docker порт 6080 не публикуется на хост и доступен только в отдельной сети источника. Используйте `PLATONUS_DB_HOST=platonus-readers-tunnel`. База с точки зрения SSH-сервера задаётся `PLATONUS_REMOTE_MYSQL_HOST`. Пользователь SSH и MySQL — разные сущности.

После заполнения окружения (выполнять только с разрешением владельца) соберите исполнитель и примените конфигурацию API:

```sh
docker compose --env-file .env.server --env-file .env.readers \
  -f compose.server.yaml -f compose.readers.yaml build readers-sync
docker compose --env-file .env.server --env-file .env.readers \
  -f compose.server.yaml -f compose.readers.yaml up -d --build --wait api
```

Затем запустите туннель:

```sh
docker compose --env-file .env.server --env-file .env.readers \
  -f compose.server.yaml -f compose.readers.yaml \
  --profile readers-tunnel up -d --build platonus-readers-tunnel
```

Процесс имеет restart unless-stopped, ExitOnForwardFailure, keepalive 30/3 и StrictHostKeyChecking. Для приложения вне Docker:

```sh
ssh -N -T -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 \
  -o ServerAliveCountMax=3 -o StrictHostKeyChecking=yes -i /path/to/key \
  -L 127.0.0.1:6080:MYSQL_HOST_FROM_SSH_SERVER:3306 SSH_USER@SSH_HOST
```

Для частного CA MySQL/AD смонтируйте файл read-only в readers-sync и укажите контейнерный путь. Настроенный MySQL CA включает проверку hostname; адрес туннеля должен соответствовать сертификату через подтверждённое сетевое имя. Не отключайте проверку ради запуска.

## Команды и безопасность синхронизации

Исполнитель использует ту же БД и миграции. Сначала проверка, потом отдельное решение о реальном импорте:

```sh
./deploy/readers/run.sh platonus --dry-run --limit 10 --no-photos --year 2026
./deploy/readers/run.sh active_directory --dry-run --limit 10 --no-photos
./deploy/readers/run.sh platonus-personal --dry-run --limit 10
./deploy/readers/run.sh csv --file /import/readers.csv --dry-run
```

`reader-import/` — локальная папка оператора, read-only внутри /import, не в Git. CSV UTF-8: `ticket_number,iin,birth_date`, дата YYYY-MM-DD; вместо билета допускается barcode либо единственный подтверждённый источником login. CSV не создаёт людей. Неоднозначные совпадения отклоняются. ИИН сохраняет ведущие нули, проверяются дата/контрольная сумма/уникальность. По умолчанию ИИН и дата дополняют пустые поля; `--overwrite` — явное замещение. ИИН преподавателей из students никогда не ищется.

Весь источник сначала читается во временный непубличный файл, затем обрабатывается пакетами. Одна общая PostgreSQL advisory lock защищает все команды, включая CSV и personal-data. Повторный запуск использует `(source,entity_type,external_id)`; одинаковые StudentID/TutorID не смешиваются. AD имеет приоритет в полях, которыми уже управляет AD. Ручные переопределения сохраняются. Библиотечный статус/лимиты, история, роли сотрудников и постоянный билет обычным импортом не заменяются.

`--dry-run` откатывает изменения читателей, фото и счётчиков; сохраняется только технический журнал запуска. `--no-photos` исключает фотографии. `--limit` всегда исключает приостановление отсутствующих. `--deactivate-missing` требует полного успешного непустого ответа, подтверждённых правил статусов и доли не ниже `READER_SYNC_MIN_RATIO` (0.8). Ошибки, сетевой обрыв, пустой/короткий ответ запрещают приостановление. Люди с другим источником и ручными блокировками сохраняются. Никто не удаляется. Конфликты видны администратору в «Синхронизация»; автоматического объединения неоднозначных карточек нет.

Расписание: `deploy/readers/schedule.example`, отключено комментариями. Указан UTC; примеры 03:20/03:50/04:10 UTC = 08:20/08:50/09:10 Алматы. Владелец согласует непиковое время. Проверить поддержку CRON_TZ у установленного cron; иначе применить systemd timer с явным UTC. Общая блокировка, а не разница времён, предотвращает пересечения. Наличие расписания не означает успешного подключения.

## Проверка без внешних систем

Синтетический JSONL для `--fixture` имеет строки:

```json
{"entity_type":"student","external_id":"fixture-1","fields":{"full_name":"Тестовый читатель","category":"student","faculty":"Тестовый факультет"}}
```

Использовать только отдельную тестовую БД; обычный запуск без dry-run сохраняет fixture как источник platonus. Для HTTP тестов используется изолированная SQLite; конкурентные проверки запускаются на disposable PostgreSQL с `TEST_READERS_DATABASE_URL`, создавая собственную временную схему. Нельзя указывать производственную БД для тестов.

```sh
python -m pytest -q tests/test_readers.py tests/test_readers_postgres.py
```

Источник `/Users/amirahmetov/work/library` использован только для чтения правил и схемы. Реальные AD/Platonus, массовый импорт и публикация на сервере требуют отдельного согласованного этапа.

При подключении внешнего reverse proxy его журнал также должен использовать `$uri` вместо `$request`/`$request_uri`: поисковые параметры могут содержать ИИН. Встроенный Nginx и Uvicorn уже исключают значения поиска из access log. Не включайте отладочное журналирование SQL-параметров, LDAP ответов или HTTP-тел запросов.

`AD_CATEGORY_MAP` сопоставляет подтверждённые значения employeeType с библиотечными категориями. Без него общая категория `AD_DEFAULT_CATEGORY` применяется только к новой карточке: уже установленная подробная категория Platonus не заменяется на staff. Для отображения тех же настроек в API подключите overlay `compose.readers.yaml` при обновлении API; одного окружения исполнителя недостаточно:

```sh
docker compose --env-file .env.server --env-file .env.readers \
  -f compose.server.yaml -f compose.readers.yaml up -d --build api
```

Сам запуск API не синхронизирует людей и не подключается к источникам. SSH-ключ на хосте должен иметь ограниченные права чтения (например, 0600); контейнер не изменяет смонтированный ключ.

### Один запуск всех источников

После заполнения `.env.readers` и запуска туннеля выполните сначала проверку:

```sh
./deploy/readers/run.sh all --dry-run
```

После проверки отчётов загрузка:

```sh
./deploy/readers/run.sh all
```

Последовательность: AD → Platonus (люди) → Platonus (ИИН/даты рождения).
Ошибка останавливает цепочку. Оба источника должны быть включены; если нужен
один, укажите его вместо `all`. Проверочный запуск каждого этапа откатывается,
поэтому этап ИИН проверяет только уже существующие локальные связи. Для первых
полных данных он выполняется после фактической загрузки людей. Запуск `all`
не приостанавливает отсутствующих людей; это отдельная настройка после сверки
статусов и полноты источников. Расписание показано в deploy/readers/schedule.example.

В существующей `.env.readers` замените `AD_PLATONUS_LINK_CONFIRMED=false` на
`true`, если используете те же platonusUserId/platonusUserType, что в образце.
Все адреса, bind/MySQL-пароли, SSH-ключ и CA задаются отдельно; они не
копируются из старого приложения. Настройки не подключают источники сами:
реальный импорт запускает администратор указанными командами.


## Печать читательского билета

В карточке читателя нажмите «Читательский билет». Откроется отдельный экран
«Печать / Назад» по макету прежнего проекта: название университета, ФИО,
категория и кафедра, Code 128, QR-код, номер билета. Фото в этот макет не входит.
Оба кода содержат только постоянный штрихкод читателя (RDR…), а не ИИН
или персональные данные; они подходят для поиска/регистрации посещений.

Размер билета — 86 × 54 мм. PDF/страница печати — 94 × 62 мм с полями 4 мм.
При печати масштаб 100%, колонтитулы отключены. В диалоге браузера можно
выбрать принтер или «Сохранить как PDF». Меню и кнопки на бумагу не выводятся.
Требуется право readers.ticket.print; открытие печатного билета аудируется.
READER_TICKET_BRAND позволяет изменить название университета; по умолчанию
используется английское название из проекта-образца.

## Ночное обновление и загрузка одного человека

В «Читателях» кнопка **Найти в AD / Platonus** позволяет искать по ФИО
или логину (от 3 символов), проверить группу/подразделение и загрузить выбранного
человека. Не более 20 результатов; при большем количестве уточните запрос.
Для сотрудников администратор выдаёт право **Поиск и загрузка читателей из AD / Platonus**
и право просмотра реестра. Администратору доступны оба действия автоматически.
Карточка перечитывается из источника при импорте; присланные браузером ФИО не используются.
Повторный импорт по идентификатору источника обновляет ту же карточку, сохраняет
билет, ручные переопределения и историю посещений. StudentID и TutorID различаются.
Новый активный студент доступен для ручной загрузки даже до назначения учебной группы.

Для постоянной работы требуется `.env.readers` с действующими настройками источников
(см. `.env.readers.example`), доверенный сертификат AD в `deploy/readers/certs/`
и SSH-ключ **сервера**, которому разрешён туннель к Platonus. Локальный `.env.readers`
и SSH-пути Mac на сервер переносить вслепую нельзя. Проверка TLS и SSH host key обязательна.
`PLATONUS_REMOTE_MYSQL_PORT` — порт на удалённой стороне туннеля, обычно 3306;
у существующего прокси может быть 6080. AD_HOST должен разрешаться внутри контейнеров.
API и планировщик используют одинаковые источники и сеть readers-source.

```sh
# На сервере, после заполнения .env.readers:
./deploy/readers/nightly.sh
# На локальном компьютере:
READERS_LOCAL=1 ./deploy/readers/nightly.sh
```

Сервис `readers-scheduler` работает постоянно и перезапускается Docker автоматически.
`READERS_NIGHTLY_ENABLED=true`, `READERS_NIGHTLY_TIME=03:20`: ежедневно по времени
Алматы, независимо от часового пояса Linux. Сначала AD, затем Platonus, затем
персональные данные студентов. При первом запуске после назначенного времени
выполняется пропущенное обновление за текущий день. Успешный запуск за день
сохраняется в БД и после перезапуска не повторяется. При обрыве источника —
повтор через час, максимум три попытки за день. Отдельные некорректные карточки
попадают в журнал, не препятствуя обработке остальных источников. Если полный
этап AD не удалось прочитать/зафиксировать, Platonus в этой попытке не запускается.
Отсутствующие люди автоматически не удаляются. Настройки ручных блокировок сохраняются.

В «Синхронизации» доступны расписание и история запусков (включая «Ночное обновление»).
Наличие расписания в настройках само по себе не доказывает, что контейнер запущен:
проверяйте состояние `readers-scheduler` и журнал. Ночью компьютер/сервер и Docker
должны работать и иметь доступ к AD/Platonus. Старые cron-задания этой синхронизации
нужно отключить. На Mac при сне обновление выполнится после пробуждения.
Без повторного подключения overlay при пересоздании API онлайн-поиск потеряет настройки;
для обновления используйте nightly.sh (основной web обновляется обычным способом).

Все подключения к источникам выполняют только чтение. Секреты, сертификаты
локальной среды и настройки DNS не публикуются в Git. Старый сайт не изменяется.

Для внепланового полного запуска после исправления подключения:
```sh
docker compose --env-file .env.server --env-file .env.readers \
  -f compose.server.yaml -f compose.readers.yaml \
  exec readers-scheduler python -m app.reader_scheduler --run-now
```
Результат проверяйте в «Читатели → Синхронизация». Эта команда записывает запуск
в тот же журнал и использует ту же защиту от одновременного запуска.
