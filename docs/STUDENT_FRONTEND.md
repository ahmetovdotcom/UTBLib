# library — публичный интерфейс UTBLib

Актуально на 4 ноября 2026. `library` (ветка `audit`) и UTBLib остаются отдельными
приложениями, но библиотечные данные принадлежат только UTBLib.

Серверное обновление: [пошаговая инструкция](PRODUCTION_STUDENT_FRONTEND.md).

## Кто за что отвечает

- **UTBLib**: каталог MARC, экземпляры и их доступность, читатели, билеты, выдачи,
  возвраты, сроки, бронирования, штрафы, инциденты, посещения; публикации сайта.
- **library**: готовый дизайн, публичные страницы, вход через AD, сессии и отображение
  личного кабинета. Его локальная БД нужна для идентичностей пользователей, аудита входа
  и Laravel; каталог, билеты и историю из неё в этом режиме не показываем.
- **AD** проверяет университетский логин и пароль по LDAPS. Пароль не передаётся в
  UTBLib и не сохраняется в `library`. Публичный каталог доступен без входа.
- Читатели синхронизируются с AD/Platonus только штатными задачами UTBLib.

## Какие страницы подключены

Главная (число записей/экземпляров и новые поступления), каталог и карточки,
новости, мероприятия, ресурсы, репозиторий. Публикации появляются после публикации
сотрудником в UTBLib. Неопубликованные записи сайта и служебные поля не выдаются.
Статические тексты, дизайн и контакты остаются частью интерфейса `library`.

Кабинет `/dashboard`: текущие выдачи и сроки возврата, просрочки, существующий
читательский билет с QR/штрихкодом, история, бронирования, штрафы, инциденты,
посещения, учебные/контактные данные и фото. QR на билете — код существующего
билета, **не ссылка для входа**. Ранее отменённый вход студентов по QR не возвращён.

Кабинет работает только на чтение. Продление, выдачу, возврат, бронирование и
исправления оформляет сотрудник в UTBLib. Старые кабинеты сотрудников `library`,
API локальной книговыдачи и локальные операции читателя закрыты в режиме frontend.
Старая очередь и планировщик `library` не запускаются контейнером в этом режиме.
Избранная подборка хранится в отдельной сессии браузера и не является бронированием.
Старый AI-помощник скрыт: его инструменты привязаны к прежней базе.

## Связь с учётной записью

После настоящей проверки пароля AD сервер сохраняет `objectGUID` в сессии.
Для запроса личных данных `library` подписывает HMAC-SHA256:

```
GET
/api/student/v1/me
section=loans&page=1
<canonical lowercase AD objectGUID>
<unix timestamp>
```

Подпись, GUID и время передаются заголовками `X-Reader-Signature`,
`X-Reader-Subject`, `X-Reader-Time`; допустимый сдвиг времени — 60 секунд.
Ключ хранится только на двух backend. UTBLib находит единственную связь в
`reader_identities` (`source=active_directory`, `entity_type=ad_user`). Совпадение
ФИО, почты, логина или переданный браузером `reader_id` не дают доступа к карточке.
Одинаковое имя у нескольких людей безопасно; конфликт GUID закрывает доступ.
Повторно использованный AD-логин не присваивает прежнюю локальную идентичность.

Если связи нет, студент видит просьбу обратиться к библиотекарю. В UTBLib нужно
импортировать/обновить человека из AD и штатно подтвердить связь с имеющейся
карточкой Platonus. Новый билет при входе автоматически не создаётся.

API: `GET /api/student/v1/me` и `/photo`. Разделы: overview, loans, history,
reservations, fines, incidents, visits, profile, card. Страницы по 50 записей.
Личные ответы `private, no-store`; общий каталог использует публичную проекцию.
Сбой UTBLib даёт сообщение о недоступности, без возврата к старой базе.
Главная кэширует публичные блоки на 5–15 минут; личные выдачи и наличие в карточке
запрашиваются заново. Административный ключ UTBLib для этой связи не используется.

## Конфигурация

В приватном окружении **обоих** backend задайте одинаковый случайный
`STUDENT_BRIDGE_KEY` (не менее 32 символов; можно создать `openssl rand -hex 32`).
Не публикуйте ключ в Git, JavaScript, URL или журналах. Он доверяет frontend
выбор читателя, поэтому доступ к нему должен быть только у серверных процессов.

В `.env` проекта **library**:

```dotenv
UTBLIB_FRONTEND_ONLY=true
UTBLIB_CATALOG_URL=http://utblib-web
UTBLIB_CATALOG_TIMEOUT=10
STUDENT_BRIDGE_KEY=<тот же отдельный случайный ключ>
AD_ENABLED=true
AD_USE_SSL=true
AD_REQUIRE_CERT=true
APP_DEMO_LOGIN_ENABLED=false
```

Адрес выше — пример имени сервиса внутри общей Docker-сети; задайте реальный
адрес UTBLib, доступный **из контейнера library**. `127.0.0.1` внутри одного
контейнера не адрес другого. Межсерверный трафик вне закрытой Docker-сети — HTTPS.
Сохраните существующие AD_HOST, AD_PORT, AD_BIND_DN, AD_BIND_PASSWORD, AD_BASE_DN,
AD_USER_FILTER и доступный контейнеру AD_CA_CERT_PATH. Проверку сертификата не отключать.
Нужны доступ к DNS/контроллеру AD и согласованное время двух серверов.
На публичном домене обязательны HTTPS, production APP_ENV/APP_DEBUG=false и
защищённые cookie. Не открывать PostgreSQL, LDAPS или служебный ключ посетителям.

В `.env.server` **UTBLib** добавляется только `STUDENT_BRIDGE_KEY`.
Новая миграция не нужна. После обновления необходимо **пересоздать** API UTBLib
с сохранением действующих Compose overlays, а в library пересобрать app и ресурсы
Vite. Простой `restart` не применяет новые переменные окружения контейнера.
Не запускать миграцию/очистку/повторный импорт каталогов ради подключения frontend.
Не запускать legacy installer UTBLib поверх этого frontend: он устанавливает
только старый публичный адаптер и не содержит изменения AD/кабинета этой ветки.
